# 🎯 PROJECT REQUIREMENTS - ZUNO MARKETPLACE ABIS

## 📋 OVERVIEW
**Project Name:** Zuno Marketplace ABIs  
**Type:** ABI Registry & Management Platform (Backend API + Basic UI)  
**Purpose:** Central registry for developers to store, manage, and share Smart Contract ABIs across multiple blockchain networks for various applications that require contract addresses and their corresponding ABIs.

---

## 🎯 MAIN OBJECTIVES

### Core Functionality:
1. **ABI Storage** - Manage Smart Contract ABIs
2. **Version Control** - Track ABI versions with changelog
3. **Multi-chain Support** - Support multiple blockchain networks
4. **Contract Registry** - Link contracts to their respective ABIs
5. **API Access** - REST API with authentication and rate limiting
6. **IPFS Backup** - Permanent storage for ABIs
7. **Header Version API** - Manage API version through headers
8. **Cache DB with Redis**
9. **Store ABIs in IPFS and database**
---

## 🔑 CORE FEATURES

### 1. ABI Management
- ✅ Upload ABI (JSON format)
- ✅ Version control (semantic versioning: 1.0.0, 1.1.0, 2.0.0)
- ✅ Auto-increment version when updating
- ✅ Changelog tracking
- ✅ ABI deduplication (via hash)
- ✅ Soft delete (archive old ABIs)
- ✅ Search by name, standard (ERC20, ERC721, ERC1155)
- ✅ Tag system for categorization
- ✅ Automatic IPFS backup

**Design Principles:**
- ABIs are **generic** (not specific to any single network)
- One ABI may be used for contracts on multiple chains
- Network relationships are defined via the contracts table

### 2. Contract Registry
- ✅ Register contracts with address + network + ABI
- ✅ Multi-chain support (Ethereum, Polygon, BSC, Arbitrum, etc.)
- ✅ Contract verification tracking
- ✅ Proxy pattern detection
- ✅ Deployment info (deployer, timestamp)
- ✅ Contract metadata (symbol, decimals, totalSupply)
- ✅ Link contracts to ABIs
- ✅ Unique constraint (address + network)

**Design Principles:**
- Contract = Address + Network + ABI (all are required)
- A single ABI can be on multiple chains
- Contracts MUST have an ABI (cannot be null)


### 4. Authentication & Authorization
- ✅ Better Auth integration
    -Api key, ratelimit, ...

- ✅ API Key Management
  - Personal keys (user-specific)
  - Organization keys (team access)
  - Public keys (read-only marketplace access)
  - Key metadata (scopes, IP whitelist, allowed origins)
  
- ✅ Rate Limiting
  - Built-in Better Auth rate limiting
  - Per-key limits (free: 100/hour, pro: 1000/hour, enterprise: 10000/hour)
  - Sliding window algorithm
  - Rate limit headers (X-RateLimit-Remaining, X-RateLimit-Reset)

### 5. Caching Strategy
- ✅ Upstash Redis
  - Cache ABIs (1 hour TTL)
  - Cache contracts (1 hour TTL)
  - Cache search results (5 minutes TTL)
  - Cache headers (Cache-Control, ETag)

### 6. IPFS Integration
- ✅ Pinata for IPFS pinning
  - Auto-upload ABIs to IPFS on create/update
  - Store IPFS hash + URL
  - Permanent backup
  - Content-addressed storage

### 7. Audit & Monitoring
- ✅ Audit logs
  - Track all API requests
  - User/API key attribution
  - Request/response metadata
  - Duration tracking
  
- ✅ Logging (Custom logger or Sentry optional)
  - Error tracking
  - Performance monitoring
  - Health checks via cron job

## 💾 DATABASE SCHEMA

### Core Tables:

**1. networks** - Blockchain networks
- chainId (unique)
- name, slug
- RPC URLs, explorer URLs
- Native currency info
- Indexes: chainId, slug

**2. abis** - ABI definitions (generic, multi-chain)
- userId (owner)
- name, description, contractName
- abi (JSONB), abiHash (unique)
- ipfsHash, ipfsUrl
- version, tags, standard
- metadata (compiler, license, originNetwork, compatibleNetworks)
- soft delete (isDeleted, deletedAt)
- **NO networkId** - ABI is generic
- Indexes: userId, abiHash, name, standard

**3. abiVersions** - Version history
- abiId (foreign key)
- version, versionNumber
- abi (JSONB), abiHash
- ipfsHash, ipfsUrl
- changeLog
- metadata (breaking, deprecated)
- Unique constraint: (abiId, versionNumber)
- Indexes: abiId, (abiId + versionNumber)

**4. contracts** - Deployed contracts
- address (0x...)
- networkId (required) - foreign key to networks
- abiId (required) - foreign key to abis
- name, type (token, nft, defi, dao)
- isVerified, verifiedAt, verificationSource
- metadata (symbol, decimals, isProxy, implementation)
- deployedAt, deployer
- Unique constraint: (address + networkId)
- Indexes: (address + networkId), abiId

**5. auditLogs** - API usage tracking
- userId, apiKeyId
- method, path, action
- ipAddress, userAgent
- resourceType, resourceId
- statusCode, duration
- metadata (error, requestBody)

### Better Auth Tables:
- user
- session
- account
- verification
- apiKey (with built-in rate limiting fields)
